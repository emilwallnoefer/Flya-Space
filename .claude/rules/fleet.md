# Fleet (beta)

Paths below are relative to `web/src/` unless they start with `public/`, `scripts/` or `supabase/` (all under `web/`).

- **Fleet (beta)** — material tracking + day-level booking (inclusive `start_date`/`end_date`; `end_date` is the due date), in `components/fleet/` (`fleet-panel.tsx` + `day-grid.tsx` + `manage-material.tsx` + `asset-icon.tsx` + `reliability-badge.tsx`), mounted lazily from `dashboard-shell.tsx` and opened from the burger menu, its card on the workspace home, or `?module=fleet` deep links. Pure rules in `lib/fleet-rules.ts` (day math, conflict checks, reliability score, reminder schedule — all `Date.now()`-free and covered by `fleet-rules.test.ts`); server reads in `lib/fleet-queries.ts`; all writes through `app/api/fleet/route.ts` on the service-role client, since the booking horizon and queue order cannot be expressed as RLS. Reminders: `app/api/cron/fleet-return-reminder/`. Migrations: `supabase/2026-09-01-fleet-management.sql` (needs `btree_gist`), then `2026-09-01-fleet-holder-claims.sql` (lets a booking be filed under a NAME with a null `user_id`, adds the claim flow + `fleet_settings`), then `2026-09-01-fleet-assigned-pool.sql` (`fleet_assets.pooled` splits the bookable pool from fixed assignments; only pooled units render in the calendar), then `2026-09-15-fleet-claim-oversight.sql` (`self_match` + `claimed_label` on `fleet_holder_aliases`, and withdraws the unused `authenticated` select grant). Claiming a holder label is **deliberately permissive** — the sheet spelled people inconsistently, so a strict name match would strand the people the flow exists to onboard; a mismatch is recorded, mailed to `ADMIN_EMAILS`, and fixable from Admin → Holder claims (`app/api/admin/fleet-holder-claims/`). All of them are **structure only** — the material list is entered through the app (Fleet → Manage, admin only), never seeded. The reliability score is **derived, never stored** — keep it that way, or it will drift from the history it summarises. Two invariants that protect trust in it: rows with `source = 'sheet_import'` never affect anyone's score, and an unclaimed booking (`user_id` null) can never trigger a reminder.
- **Edge cases (plan: `web/docs/fleet-edge-cases.md`, P1 landed 2026-10-19 via `supabase/2026-10-19-fleet-edge-cases-1.sql`).** A `picked_up` booking past its due date **blocks through today** (`blockedUntil` in `lib/fleet-rules.ts`): the grid paints those days taken, `checkReservation` refuses them, and `check_out` refuses a unit whose asset is `out` with someone else — the DB exclusion constraint cannot express this, so the API check is the guard. `daysOverdue` counts only `picked_up`; a `reserved` booking whose span has passed is a **no-show**, closed by the daily reminder cron (`expiryFor`) as `cancelled` + `closed_reason = 'no_show'` with a mild, capped score penalty, and a lapsed `waitlisted` row is closed as `expired` (scores nothing). `closed_reason` is written by every closing path (`cancel`, `check_in`, `closeLiveReservations`, the sweep) — keep that up when adding one. `check_in` accepts a backdated `returned_on` bounded to `[start_date, today]`. Overdue reminders stop after `OVERDUE_REMINDER_DAYS` (30), and imported bookings get wording that does not claim a score impact. `promoteWaitlist` considers every waitlisted span on the asset, not only the freed start date.
- **Extensions and requests (P2, `supabase/2026-10-19-fleet-edge-cases-2.sql`).** One action, `change_dates {reservation_id, end_date}`: the pure rules in `lib/fleet-requests.ts` (`classifyDateChange`, tested) decide shorten / extend / refuse — the last day can never move before today (that is check-in's job), growth is bounded by `MAX_RESERVATION_DAYS` and the horizon measured to the *new* end. Shortening is instant and promotes the waitlist. Extending into free days is instant; into someone else's booking it files one `fleet_booking_requests` row per colliding booking (service-role only, one pending per pair) and **changes nothing**. The next booker answers with `respond_request {request_id, reply}` — `shorten` (their start moves to the day after), `cancel`, or `decline` — and only the recipient (or an admin, always, and alone when the target is unclaimed) may answer. **Never auto-move another person's booking**: owner decision, 2026-10-18. The extension applies only when every request for it is accepted, re-checked against live spans at that moment. Requests settle themselves (`settleRequestsFor`): the requester cancelling/checking in/shortening withdraws theirs; the target being picked up, cancelled or checked in expires those against it; the daily cron expires pending requests whose target has started. The board hands each viewer only their own (`requests`, admins all); `components/fleet/requests-strip.tsx` is shared by both shells.
- **Notices (P3, `supabase/2026-10-19-fleet-edge-cases-3.sql`).** Everything the Fleet tells someone *other than the holder* goes through `lib/fleet-notify.ts#sendFleetNotice`: it claims a `fleet_notice_sends` row (reservation, recipient, kind, date — unique) **before** delivering, pushes to the person's devices via `lib/push/notify-users.ts#pushToUsers` (the one shared send/prune/stamp loop; the Friday cron, chat mentions and the phone-tour notice use it too), falls back to e-mail only when they have **no** device, honours `user_metadata.fleet_notices === false` (Settings → Notifications → Fleet, a preference not a privilege), and writes a `notice_sent` event when something went out. Renderers are pure in `lib/fleet-notices.ts` (tested); every notice deep-links to one booking (`/dashboard?module=fleet&reservation=<id>`, read next-frame by both shells, then dropped from the URL). Senders: the daily cron (`unit_not_back` two days before and on the next booker's first day — claim dated start−2 and start; `overdue_escalation` to admins at exactly day 7, unclaimed holders included), `change_dates` (`extension_request` to the recipient, or admins when the target is unclaimed), `respond_request` (`extension_accepted`/`extension_declined` to the requester), `check_in` (`unit_back_early` to the next booker when back before the due date), and `promoteWaitlist` (`waitlist_promoted`). Names in notices come from `displayNameFor()`.
- **Interchangeable units (P4, `supabase/2026-10-19-fleet-edge-cases-4.sql`).** `fleet_assets.kind_key` is an admin-set slug (Fleet → Manage → "Interchangeable with", picked from the keys in use; `normalizeKindKey` slugs whatever is typed, and a DB check enforces the shape). **Never derive siblings from `model`**: a unit with no kind has no alternatives, full stop (owner decision 2026-10-18). `freeSiblings` in `lib/fleet-rules.ts` (pure, tested) is the one rule — same kind, bookable, active, no blocking span over the whole span with overdue units counted through today — and `fetchFreeSiblings` in `lib/fleet-queries.ts` feeds it from the DB. It is surfaced in the reserve refusal (`alternatives` + the message), on incoming pending requests on the board, and in the `unit_not_back` / `extension_request` notices. `move_booking {reservation_id, asset_id}` moves an own `reserved` booking to a free unit for the same days (never a `picked_up` one — that is check-in), writes `moved_booking` on both units, and **grants any extension request that was waiting on it** (`accepted`/`move`, then `applyExtensionIfReady` in `handlers/shared.ts`, which `respond_request` shares). The hook keeps the server's last `alternatives` until the next write; both booking flows render them as "Book X instead".
