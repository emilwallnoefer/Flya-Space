# Fleet (beta)

Paths below are relative to `web/src/` unless they start with `public/`, `scripts/` or `supabase/` (all under `web/`).

- **Fleet (beta)** — material tracking + day-level booking (inclusive `start_date`/`end_date`; `end_date` is the due date), in `components/fleet/` (`fleet-panel.tsx` + `day-grid.tsx` + `manage-material.tsx` + `asset-icon.tsx` + `reliability-badge.tsx`), mounted lazily from `dashboard-shell.tsx` and opened from the burger menu, its card on the workspace home, or `?module=fleet` deep links. Pure rules in `lib/fleet-rules.ts` (day math, conflict checks, reliability score, reminder schedule — all `Date.now()`-free and covered by `fleet-rules.test.ts`); server reads in `lib/fleet-queries.ts`; all writes through `app/api/fleet/route.ts` on the service-role client, since the booking horizon and queue order cannot be expressed as RLS. Reminders: `app/api/cron/fleet-return-reminder/`. Migrations: `supabase/2026-09-01-fleet-management.sql` (needs `btree_gist`), then `2026-09-01-fleet-holder-claims.sql` (lets a booking be filed under a NAME with a null `user_id`, adds the claim flow + `fleet_settings`), then `2026-09-01-fleet-assigned-pool.sql` (`fleet_assets.pooled` splits the bookable pool from fixed assignments; only pooled units render in the calendar), then `2026-09-15-fleet-claim-oversight.sql` (`self_match` + `claimed_label` on `fleet_holder_aliases`, and withdraws the unused `authenticated` select grant). Claiming a holder label is **deliberately permissive** — the sheet spelled people inconsistently, so a strict name match would strand the people the flow exists to onboard; a mismatch is recorded, mailed to `ADMIN_EMAILS`, and fixable from Admin → Holder claims (`app/api/admin/fleet-holder-claims/`). **There is no per-unit home location** (column dropped by `2026-10-19-fleet-drop-home-location.sql`, owner decision 2026-10-19): every pooled unit lives at `FLEET_HOME_LOCATION` in `lib/fleet-rules.ts` ("Pilots HQ Lausanne") between jobs — `check_in` on a pooled unit, `return_to_pool` and a pooled `create_asset` land there unless the caller names a place, and both shells prefill "Bring back" with it. Do not re-add a home field; change the constant instead. The mirror rule: **an assigned unit (`pooled = false`) has no location** — `assign`, `update_asset` leaving the pool and a borrower's `check_in` all write `current_location = null` (it travels with its person and nobody logs where; `2026-10-19-fleet-assigned-no-location.sql` cleared the old rows). All of them are **structure only** — the material list is entered through the app (Fleet → Manage, admin only), never seeded. The reliability score is **derived, never stored** — keep it that way, or it will drift from the history it summarises. Two invariants that protect trust in it: rows with `source = 'sheet_import'` never affect anyone's score, and an unclaimed booking (`user_id` null) can never trigger a reminder.
- **Edge cases (plan: `web/docs/fleet-edge-cases.md`, P1 landed 2026-10-19 via `supabase/2026-10-19-fleet-edge-cases-1.sql`).** A `picked_up` booking past its due date **blocks through today** (`blockedUntil` in `lib/fleet-rules.ts`): the grid paints those days taken, `checkReservation` refuses them, and `check_out` refuses a unit whose asset is `out` with someone else — the DB exclusion constraint cannot express this, so the API check is the guard. `daysOverdue` counts only `picked_up`; a `reserved` booking whose span has passed is a **no-show**, closed by the daily reminder cron (`expiryFor`) as `cancelled` + `closed_reason = 'no_show'` with a mild, capped score penalty, and a lapsed `waitlisted` row is closed as `expired` (scores nothing). `closed_reason` is written by every closing path (`cancel`, `check_in`, `closeLiveReservations`, the sweep) — keep that up when adding one. `check_in` accepts a backdated `returned_on` bounded to `[start_date, today]`. Overdue reminders stop after `OVERDUE_REMINDER_DAYS` (30), and imported bookings get wording that does not claim a score impact. `promoteWaitlist` considers every waitlisted span on the asset, not only the freed start date.
- **Extensions and requests (P2, `supabase/2026-10-19-fleet-edge-cases-2.sql`).** One action, `change_dates {reservation_id, end_date}`: the pure rules in `lib/fleet-requests.ts` (`classifyDateChange`, tested) decide shorten / extend / refuse — the last day can never move before today (that is check-in's job), growth is bounded by `MAX_RESERVATION_DAYS` and the horizon measured to the *new* end. Shortening is instant and promotes the waitlist. Extending into free days is instant; into someone else's booking it files one `fleet_booking_requests` row per colliding booking (service-role only, one pending per pair) and **changes nothing**. The next booker answers with `respond_request {request_id, reply}` — `shorten` (their start moves to the day after), `cancel`, or `decline` — and only the recipient (or an admin, always, and alone when the target is unclaimed) may answer. **Never auto-move another person's booking**: owner decision, 2026-10-18. The extension applies only when every request for it is accepted, re-checked against live spans at that moment. Requests settle themselves (`settleRequestsFor`): the requester cancelling/checking in/shortening withdraws theirs; the target being picked up, cancelled or checked in expires those against it; the daily cron expires pending requests whose target has started. The board hands each viewer only their own (`requests`, admins all); `components/fleet/requests-strip.tsx` is shared by both shells.
- **Notices (P3, `supabase/2026-10-19-fleet-edge-cases-3.sql`).** Everything the Fleet tells someone *other than the holder* goes through `lib/fleet-notify.ts#sendFleetNotice`: it claims a `fleet_notice_sends` row (reservation, recipient, kind, date — unique) **before** delivering, pushes to the person's devices via `lib/push/notify-users.ts#pushToUsers` (the one shared send/prune/stamp loop; the Friday cron, chat mentions and the phone-tour notice use it too), falls back to e-mail only when they have **no** device, honours `user_metadata.fleet_notices === false` (Settings → Notifications → Fleet, a preference not a privilege), and writes a `notice_sent` event when something went out. Renderers are pure in `lib/fleet-notices.ts` (tested); every notice deep-links to one booking (`/dashboard?module=fleet&reservation=<id>`, read next-frame by both shells, then dropped from the URL). Senders: the daily cron (`unit_not_back` two days before and on the next booker's first day — claim dated start−2 and start; `overdue_escalation` to admins at exactly day 7, unclaimed holders included), `change_dates` (`extension_request` to the recipient, or admins when the target is unclaimed), `respond_request` (`extension_accepted`/`extension_declined` to the requester), `check_in` (`unit_back_early` to the next booker when back before the due date), and `promoteWaitlist` (`waitlist_promoted`). Names in notices come from `displayNameFor()`.
- **Interchangeable units (P4, revised 2026-10-19; `supabase/2026-10-19-fleet-edge-cases-4.sql` then `-5.sql`).** **Every unit of the same model (`fleet_assets.model`, "Model" in Manage, compared through `modelKey` so "Elios 3" and "elios-3" are one) stands in for every other** — owner decision 2026-10-19, replacing the admin-set `kind_key` of 2026-10-18 (and, for an hour, the type: too coarse, every drone would twin every other). A unit with no model has no siblings. Nothing else is set per unit; the `kind_key` column was dropped again by `supabase/2026-10-19-fleet-drop-kind-key.sql`, and a `kind_key` an old client still sends is stripped by the zod schema. `freeSiblings` in `lib/fleet-rules.ts` (pure, tested) is the one rule: pooled units first (bookable, active, no blocking span over the whole span with overdue units counted through today), then the model's **assigned** units (`assigned: true`, with the holder's name), for which the assignment's own open booking (`isAssignmentSpan`: `picked_up` + `source = 'sheet_import'`) is not a clash — only a borrow already booked is. `fetchFreeSiblings` in `lib/fleet-queries.ts` feeds it from the DB. Surfaced in the reserve refusal (`alternatives` + the message), on incoming pending extension requests on the board, and in the `unit_not_back` / `extension_request` notices. `move_booking {reservation_id, asset_id}` moves an own `reserved` booking to a free **pooled** unit for the same days (never a `picked_up` one — that is check-in), writes `moved_booking` on both units, and **grants any extension request that was waiting on it** (`accepted`/`move`, then `applyExtensionIfReady` in `handlers/shared.ts`, which `respond_request` shares). The hook keeps the server's last `alternatives` until the next write; both booking flows render them as "Book X instead" or "Ask Y for X".
- **Borrowing assigned material (`supabase/2026-10-19-fleet-edge-cases-5.sql`).** An assigned unit (`pooled = false`) can be **asked for, never booked outright** (owner decision 2026-10-19; the F5 audit rule "no booking on an assigned unit without the assignee" still holds — approval is that). `reserve` on one writes the booking as **`waitlisted`** (blocks nobody, invisible to the exclusion constraint) plus a `fleet_booking_requests` row of `kind = 'borrow'` (`asset_id`, `requested_start_date`/`_end_date`, `holder_label`; `target_reservation_id` is null — the table's `_shape` check enforces which columns each kind fills). The recipient is `fleet_assets.current_holder_user_id`, or the admins when the name on the unit has no account; they answer with `respond_request {reply: 'approve' | 'decline'}` (the handler refuses a reply that does not fit the kind). **Approve** re-checks the days against other borrows (`borrowCompetitors`, assignment rows excluded), calls `yieldAssignmentFor` in `lib/fleet-assignment.ts` so the assignment's booking ends the day before (or closes as returned when the borrow starts no later than it began), then flips the row to `reserved` — the exclusion constraint has the last word. **Decline** cancels the row. `promoteWaitlist` never touches a `waitlisted` row on an assigned unit. The hand-over: `check_out` on an assigned unit is the borrower taking it from the assignee (the usual "still out with X" refusal does not apply; `closeAssignmentRows` closes the assignee's booking as returned), and `check_in` puts it back with the assignee — asset `out`, holder restored from the accepted request's `recipient_id`/`holder_label`, location cleared — and `restoreAssignment` re-opens their booking for `ASSIGNMENT_SPAN_DAYS`, stopping the day before the next approved borrow. `cancel` of an approved borrow calls `restoreAssignment` too; the daily cron expires a pending borrow whose row is gone or whose days have passed. Notices: `borrow_request` to the recipient(s), `borrow_approved` / `borrow_declined` to the requester (claim keyed on the pending row). Both shells label such a row "Awaiting approval" with "Withdraw request"; the Requests strip shows Approve / Decline, and on an extension request "Ask Y for X" files a borrow for the recipient's own days (their booking stays until they answer the extension themselves).
